## Summary

This FDD covers MiLogin-based authentication/authorization for all three identity types (Citizen, Business, Worker), the security-form approval workflow, user group/role administration, inactivity deactivation, user impersonation ("View As"), and email template administration. The core Business-user authorization-request lifecycle (submit → Lead Admin one-time link → approve/deny/expire/withdraw) and the public removal-request flow are modeled thoroughly and consistently in `iam-domain.md`/`iam-sequences.md` — this is the strongest part of the alignment. The review surfaced one substantive open discrepancy that blocks a clean "Aligned" status: the FDD's Worker authorization flow (1.2.2/1.2.3 — no self-service form, zero permissions until manual admin assignment) conflicts with `iam-sequences.md`'s authentication flow, which routes Workers through the same self-service authorization-request path as Business users. Two other findings have since been resolved with direct client/product context (see §2 #2 and #3): User Impersonation (Feature 1.8) is confirmed cut in favor of a lower-risk read-only "view what the user sees" capability, and the FDD's User Group concept is flagged as an open discrepancy to confirm with the client — the RBAC model (atomic permissions bundled into scoped Roles) is the preferred design, and the source material doesn't provide strong justification that "Group" is a genuinely distinct concept rather than historically imprecise IAM terminology for the same thing. The MiLogin IDDs are, as expected, written at a technical-integration altitude that doesn't belong in a functional design package, and the Helpdesk Guide is out of scope entirely (a different system's support runbook).

## 2. Discrepancies

| # | Shape | Topic | Side A Says | Side B Says | Assessment | Resolution / Decision |
|---|---|---|---|---|---|---|
| 1 | FDD vs. SDD | Worker authorization flow | Main FDD Business Specifications ¶"MiLogin for Workers users..." and scenarios 56-58; Feature 1.2.2/1.2.3: a new Worker account gets **zero functional permissions/roles** on first login, is **never routed through the Security Authorization Form** ("bypasses" it), and can only be assigned roles by a System Admin via User Account Search after an **offline** manager/office-director approval process. There is no Worker self-service request form at all. | `iam-sequences.md` § "MiLogin Integration - Authentication (OIDC)": the `alt` branch for "No authorizations AND MiLogin type = Business/Worker" is a single shared branch — it checks Lead Admin via Organizations API and, if the user is not a Lead Admin, redirects to the **authorization request form** (the same self-service form Business users use). `iam-domain.md`'s `AuthorizationRequest` aggregate makes no MiLogin-type distinction that would prevent a Worker from submitting a request. | Genuine conflict, not just terminology. The FDD explicitly designs Workers *out* of the self-service/Lead-Admin-approval pipeline; the SDD's authentication sequence explicitly routes them *into* it (conflated with Business). This affects a real design decision: does Worker onboarding ever produce a `AuthorizationRequest` in `Pending` status, or does a Worker account only ever move `None → Active` via `iam.authorization.grant` (System Admin Manual Authorization Grant sequence)? | **Needs Decision.** Recommend updating `iam-sequences.md`'s MiLogin Integration - Authentication diagram to split the "No authorizations" branch by MiLogin type: Business → authorization request form (current behavior); Worker → dead-end/pending-assignment state with no form, visible only via `/users/search` to a System Admin. This also implies `AuthorizationRequest.milogin_type` should probably never be `Worker` in practice, which is worth an explicit invariant in `iam-domain.md` if the decision confirms the FDD's reading. |
| 2 | SDD vs. itself — **RESOLVED** | User Impersonation / "View As" (Feature 1.8) | Fully specified by the FDD as an in-scope, required feature: System Admin (and other functional admins) can impersonate Citizen and Business users read-only, with a visible banner, entity toggling, and — critically — Feature 1.8.4 requires the capability be **restricted by the impersonating admin's own functional role** (Credential Admin → Credential/Citizen only; Staffing Admin → School District/Staffing only; System Admin → all; Identity Admin → none). | Was internally inconsistent within the SDD: `iam-permissions.md` lists `iam.user.impersonate` as a live, system-wide permission; `iam-technical-visual-summary.md` §6 diagrams "Impersonation: Read-Only Mode"; but `iam-technical-design.md` § "Omission of User Impersonation" states it "was designed and evaluated for this domain but was deliberately excluded from the initial implementation." `iam-api.yml` has no impersonation endpoint, corroborating the technical-design doc. | **Resolved with client context (not from the FDD/SDD text alone):** the client previously agreed to remove true impersonation (an admin operating *as* the user, session takeover) in favor of a lower-risk, read-only capability to see the same information the user sees — simpler and less exposed from a security standpoint than full "View As." `iam-technical-design.md`'s "deliberately excluded" note reflects the correct, current decision. `iam-permissions.md` and `iam-technical-visual-summary.md` are the stale documents. | **Action, not just a decision:** update `iam-permissions.md` to drop `iam.user.impersonate` as a session-takeover permission and replace it with a narrower read-only "view user context" capability (name TBD, e.g. `iam.user.view-context`) that surfaces data only, with no ability to act as the user; update `iam-technical-visual-summary.md` §6 to match; keep `iam-technical-design.md`'s rationale but update it to describe the read-only replacement rather than a flat omission. FDD Feature 1.8's role-scoped restriction on *who* can view *whose* context (1.8.4) still applies to the replacement capability and should be modeled — see Coverage Gap #2 (updated). |
| 3 | FDD vs. SDD — **DECIDED (2026-08-14), pending client concurrence** | User Group / Role / Functional Area / Permission-level model | Main FDD + Role Matrix (`MiEdWorkforce Role Matrix-Revised.xlsx`) model permissions as a **matrix**: `Group` (System Administrator, Credential, Staffing, EPP, Professional Learning, Data Quality, Citizen) × `Role` × `Functional Area` × `Function` (e.g., "Personnel search", "Credential Information", "Worklist") × permission level (`View`/`Edit`/`Add`/`No`). Feature 1.5.3 frames this as Functional Area → Function → per-function permission-level assignment, with Functional Areas/Functions fixed as "code-based/developer-maintained." | `iam-domain.md`'s `RoleDefinition` aggregate models a `Role` as a named bundle of atomic `Permission` value objects (`{domain}.{resource}.{action}`), assignable at a scope (System-wide/Entity/District/ISD/etc. per `iam-permissions.md`'s scope enum) — i.e. an RBAC model where "who can do what, where" is entirely captured by Role + Scope. `UserGroup` in the SDD is documented only as a lightweight "Value Object — Categorization for role organization" attached to `Role`, not a first-class administrable entity. | **Do not resolve this by simply building what the FDD asks for.** The client has historically been imprecise about IAM terminology, and prior discussion (before the ~7-month pause on this work) was already exploring whether "Group" is anything more than the client's term for a scoped Role Assignment. Nothing in the FDD, Role Matrix, or Groups-and-Roles spreadsheet makes a case for Group being conceptually distinct from Role-at-a-scope — the matrix's `Group × Role × Functional Area × Function` structure is consistent with `Group` just being an informal label a Role happens to carry, not a separate authorization primitive with its own rules. The RBAC approach (atomic permissions → Roles → assigned at a Scope) is the preferred design going forward. | **Decided.** Role + Scope only — no `UserGroup` aggregate. Across every FDD reviewed touching this concept (this one's own inconsistent Group taxonomy, FDD 05/06's "Internal Comment Group" resolving to a single PPR-access boundary check, FDD 12's orphaned `iam.group.*` permissions with no backing implementation), "Group" never carried behavior Role + Scope couldn't already express. The one real constraint attributed to Group — a user's access stays within one MiLogin type — is now `RoleDefinition.ApplicableMiLoginTypes` (grant-time check, complementing the existing query-time "MiLogin Context Enforcement" rule). `iam-domain.md`'s `UserGroup` value object removed; `iam-permissions.md`'s four `iam.group.*` permissions removed (unimplemented, no aggregate to back them). See `client-questions.md` #2 — this is the team's settled technical direction, pending final client concurrence rather than an open design question. |
| 4 | FDD vs. itself | FDD's own Group taxonomy vs. its own Role Matrix | Main FDD narrative (Business Specifications, scenario 69) lists exactly seven User Groups: System Administrator, Credential, Staffing, EPP, Professional Learning, Data Quality, Citizen. | The FDD's own `MiEdWorkforce Role Matrix-Revised.xlsx` and `Working/User Groups and Roles.xlsx` instead show Groups including System Admin, Credential, Rapbacks, Staffing, Audit, ISD Audit, School District/ISD, EPP, Professional Learning, Citizens — i.e., "Data Quality" does not appear as a top-level Group in the matrix (it appears as a Role/Epic elsewhere), while "Rapbacks," "Audit," and "School District" appear as Groups in the matrix but are absent from the main narrative's list of seven. | Not an SDD problem — noted here so the SDD isn't "corrected" to match an internally inconsistent FDD group list. This inconsistency is itself weak evidence for Discrepancy #3's hypothesis: if "Group" were a rigorously governed concept, the client's own documents would agree on what the groups are. | Recorded as an Open Question back to the client (see below), not an SDD action item. |
