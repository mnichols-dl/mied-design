## Summary

This is the first review of the `payments` domain itself, which — unlike credentialing at the
start of this series — already has a complete SDD (capability doc, permissions, sequences,
technical-design, and API spec). The main FDD narrative aligns well at the business-rule level
(PCI non-handling of card data, immutable pre-calculated fee amount, posting-file-as-source-of-
truth reconciliation, CEPAS-down error handling), and the scenarios spreadsheet mostly
corroborates decisions already made in the SDD. However, the review surfaces one substantive,
previously-undetected **cross-domain integration mismatch**: `credentialing-domain.md` and
`credentialing-sequences.md` both assume a `payments` event named `PaymentReceived` and an
endpoint named `GET /payment-status?applicationId={id}` — neither exists anywhere in
`payments-capability.md`, `payments-sequences.md`, or `payments-api.yml` (the real event is
`PaymentCompleted`; the real endpoint is `GET /payments/search?applicationId=`, a paginated
search endpoint, not a status lookup). The FDD itself never names an event or endpoint (it
describes the business behavior only), so this is an **SDD vs. itself** discrepancy the FDD
review incidentally surfaced, not something the FDD contradicts directly — but it blocks the two
domains' actual integration until reconciled. Separately, the FDD's refund process names only a
single actor (Credential Administrator) with no approval chain or dollar threshold, while
`payments-sequences.md`/`payments-permissions.md` models a two-tier ($500) dual-approval workflow
with a distinct Financial Admin role that has no FDD source. The three CEPAS Interface Design
Documents are, as expected, Boundary Violations — wire-format/API-contract specifications for an
external Treasury system, the same shape as the MiLogin and MTTC IDDs already flagged in prior
reviews — and one of them (CEPAS Payments) embeds what appears to be a live AES-GCM encryption
key value, which is a sharper concern than an ordinary altitude finding.

## Cross-Domain Question: Payment Link / Event Name / Academic Year (asked directly of this review)

**Does `payments-capability.md`/`payments-sequences.md` model the application-specific payment-link pattern credentialing's sequences assume?** Yes, structurally — `PaymentTransaction` is created per-application (`application_id FK`), the "Individual Payment Flow" sequence is keyed off `applicationId` in `GET /payments/initiate?applicationId=APP-123`, and `credentialing-sequences.md`'s "payment link will be emailed to the educator" language is consistent with payments' redirect-based, per-application initiation model. The pattern itself is aligned.

**Is the event name confirmed?** No — this is the one substantive, blocking finding of this review. `credentialing-domain.md` and `credentialing-sequences.md` both name the awaited event `PaymentReceived`. The actual event `payments-capability.md` publishes for this purpose is `PaymentCompleted` (fired after hash validation succeeds, consumed by `credentials, audit, communications`). `PaymentReceived` does not exist anywhere in the payments domain's event catalog. This needs to be corrected on the credentialing side (see Discrepancy #1) — recommend treating `payments` as authoritative since it's the event's producer.

**Is the API shape confirmed?** No — `credentialing-sequences.md` calls a `GET /payment-status?applicationId={id}` endpoint that doesn't exist in `payments-api.yml`. The closest real endpoint, `GET /payments/search`, is a scoped, paginated, permission-gated search endpoint, not a lightweight status check, and is an awkward fit for a synchronous system-to-system gate inside the auto-approval sequence (see Discrepancy #2). This should be resolved either by adapting credentialing's call to the real search endpoint or — the recommended path — adding a purpose-built status-check endpoint to `payments-api.yml`.

**Does the "one fee per school year" rule have a payments-side concept?** No. `payments-capability.md`'s `PaymentTransaction` has no academic-year, fee-schedule-period, or per-educator dedup concept anywhere — its only relevant invariants are "amount > 0" and per-transaction immutability, and it's scoped to exactly one `application_id` (or a bulk group of them) per transaction, never to an educator-and-year pair. This is corroborated positively by the FDD itself: `Payments_Scenarios.xlsx`'s "Paying for a Permit after school year ends" scenario explicitly states the corresponding validation ("prevent people from paying fees for inactive applications") "should be on MORE validation" — i.e., the client's own documentation places this check on the MiEdWorkforce/credentialing side, not CEPAS or payments. This confirms the rule is, and is expected to remain, a **purely credentialing-side dedup/eligibility check performed before ever calling payments** — not something payments needs to model, and not something currently missing from payments' scope. The actual gap is on the credentialing side: `credentialing-domain.md`'s own Open Question #24 ("How is 'per school year' defined for payment purposes?") and the FDD-17 review's already-tracked tag-index gap (`CredentialApplication`/`IssuedCredential` — no `academic_year` field) are where this needs to be resolved; this review adds no new payments-side work item, only confirms the ownership boundary.
