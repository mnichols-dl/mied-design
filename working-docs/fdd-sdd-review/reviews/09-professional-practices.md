## Summary

This FDD is the source document for the `profpractice` domain, and it shows: `profpractice-domain.md`'s aggregates, status values, event messages, and even literal district-facing notification text (e.g. "The selected individual requires further review that may delay or deny...") were clearly drafted directly from this FDD, making this the best-aligned review in the set so far. The FDD's own self-disclosure/annual-PPR-response flow — the "Needs Responses" flag reset annually on June 30 (§9.1.8), self-disclosure form (§9.1.1), and Annual Professional Practice Review form (§9.1.3) — is fully modeled in `profpractice-domain.md` via the `Disclosure` and `ProfessionalPracticeResponse` aggregates and the computed "Annual PPR Compliance" property, which the domain doc's own Appendix explicitly maps back to "Needs Responses Flag." This directly and conclusively answers the open cross-domain question carried over from the FDD-17 review (see "Cross-Domain Question" below): **the self-disclosure questionnaire step is owned and already modeled by the Professional Practices domain**, not something Credentialing needs to host. The review does surface real problems, though: three permission-scope discrepancies where the FDD grants an action to a broader/different role than `profpractice-permissions.md` allows (question configuration, marker management, disclosure deletion); an SDD-vs-itself mismatch where `credentialing-domain.md`'s simplified `ProfessionalPracticeStatus` (`Cleared`/`UnderReview`/`Blocked`, subscribing to an event named `ProfessionalPracticeClearanceUpdated`) is out of sync with `profpractice-domain.md`'s actual, more detailed `PPRClearanceAssessment` (`Clear`/`ConditionalClearance`/`Hold`/`Blocked`, published via `PPRClearanceAssessmentChanged`); a genuine coverage gap where the PPR Clearance Assessment Rule's priority-ordered evaluation never checks "Annual PPR Compliance" / "Requires PPR Response" at all, despite the FDD implying an overdue annual response should gate new applications; and the usual heavy dose of implementation-level UI prescriptiveness (exact field types, button labels, progress-indicator text) typical of this FDD corpus.

## Cross-Domain Question (from FDD-17 review)

FDD-17's review left open whether the "Needs Responses" self-disclosure questionnaire step is owned by Professional Practices or expected to be hosted by Credentialing. This review answers it directly: **Professional Practices owns it, and already models it substantially.** This FDD (09) — the PPR domain's own source document — describes exactly this flow (self-disclosure form, Annual PPR Review form, "Needs Responses" flag/annual reset), and `profpractice-domain.md`'s `Disclosure` and `ProfessionalPracticeResponse` aggregates plus its "Annual PPR Compliance" computed property (explicitly mapped from "Needs Responses Flag" in the domain doc's own Appendix) already implement it. The remaining gap is narrower than originally framed: `profpractice-domain.md`'s PPR Clearance Assessment Rule doesn't yet factor "Annual PPR Compliance not current" into the assessment it returns to Credentialing (Coverage Gap #1 above). The `credentialing-domain.md`/`ProfessionalPracticeStatus` sync (Discrepancy #1) was an internal SDD reconciliation item and has since been fixed directly (see Open Question #1, resolved). The Annual PPR Compliance gap, however, turned out to need the client after all — the FDD describes the mechanism (reset flag forces re-disclosure) but not the severity, and that's a business-process call, not an SDD-inference question. See Open Question #3 / client-questions.md #7.
