## Summary

This FDD is titled and framed around the "MiEdWorkforce System Administrator" role, but despite its folder placement alongside the `iam`-heavy FDD 01, it turns out to be about something else almost entirely: statewide/shared administrative tooling spanning several domains, not identity/access administration. Only one short passage (Feature 12's "User Authorization related functions" bullet list and a "Define user groups/role" line item under worklist admin) touches IAM at all, and it adds no new detail beyond what FDD 01 already covers in depth — it is a one-line cross-reference, not a redescription. The document's actual substance is: (1) a SCED/Grade-Educational-Setting/CTE-CIP-to-Endorsement mapping and misalignment-audit engine (Feature 12.1) that has no home anywhere in the current SDD and that a *staffing* business rule already silently assumes exists; (2) admin-editable content management for the unauthenticated Public Landing Page and the internal Dashboard chrome (Features 12.2-12.3), which is a different kind of capability than anything in `communications-capability.md`'s Alert/EmailTemplate model; and (3) an auto-generated-plus-manually-curated Data Dictionary/reference manual (Feature 12.4), also unrepresented anywhere and partly written at an implementation-prescriptive altitude. The `iam` side is otherwise Aligned (nothing new, nothing conflicting) except for one internal SDD inconsistency this review surfaced while checking `iam-permissions.md` against `iam-domain.md` for the User Group question — see Discrepancy #1.

### Direct answer to the User-Group-vs-Role question for this FDD

**FDD 12 does not settle it, and provides no new direct evidence either way.** It mentions "User groups" only as a one-line admin-page menu item (twice — once under general worklist admin, once under the User Authorization admin page), with zero description of Group's lifecycle, membership, or constraints — not enough to distinguish "a real governed entity" from "a label on a Role assignment." Its own Admin Role table (MiEdWorkforce Admin (Shared) / Credential Admin (MDE) / Staffing Admin (CEPI)) is a different, narrower concept (a 3-item page-access matrix) and should not be read as a fourth data point on the 7-item-vs-larger Group taxonomy question from the 01-user-management review — it doesn't purport to be an exhaustive Group list at all.

What this review *did* find, independently of the FDD, is a pre-existing internal SDD inconsistency worth folding into the client-questions framing: `iam-permissions.md` already catalogs `iam.group.create/edit/delete` with member-level semantics ("add/remove users"), which reads like Group was treated as a real entity at some point — yet `iam-domain.md` documents `UserGroup` as label-only, and neither `iam-sequences.md` nor `iam-api.yml` has any sequence or endpoint implementing group CRUD or membership at all. The four `iam.group.*` permissions are effectively orphaned today. This doesn't answer the question, but it means the SDD itself has not yet been reconciled around either answer — see Discrepancy #1 above and the `client-questions.md` update.
