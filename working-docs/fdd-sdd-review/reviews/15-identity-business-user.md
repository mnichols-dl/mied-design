## Summary

This is the full staffing-side identity-management process that FDD 24 (`24-request-for-id.md`, already reviewed) only entered through its narrower "Add New Employee" doorway. The SDD's existing `EmployeeRoster`/`ID_RESOLUTION_REQUESTS` modeling holds up well for that narrower path, but three real gaps surfaced once the fuller picture (demographics updates, near-match resolution in full, bulk/API ingestion, link/split/retire) was checked: (1) `staffing-sequences.md`'s "Update Employee Demographics" sequence and `staffing-api.yml`'s demographics-update endpoint had **no Near Match branch at all**, despite FDD 15.1/15.3 requiring one with materially different rules than the Add-New-Employee near-match path (no "Request New ID" option, an SSN-mismatch warning, a replace-master-record Yes/No question, and an auto-cancel timeout) — **fixed directly** in both files. (2) FDD 24's own deferred Discrepancy #2 — whether a dedicated "Identity Admin" permission should exist, since `staffing-api.yml`'s `/admin/new-id-requests/*` endpoints were documented as "Identity Admin role only" but gated by the unrelated `staffing.admin.manage-collections` — is resolved by FDD 15.9, which describes Identity Administrator as a distinct role with its own worklist and admin surface; a new `staffing.identity-admin.*` permission category was added and the two endpoints repointed to it. (3) FDD 15.6's "Link IDs" workflow — a real Business-User-initiated, Identity-Admin-approved request with its own wireframes, worklist, and status lifecycle — is **entirely unmodeled** anywhere in the SDD (no aggregate, permission, sequence, or endpoint), and FDD 15.5's bulk/API file-upload feature (common file staging area, schema validation, sandbox commit/cancel, async Mi-Key processing) is likewise absent from `staffing-domain.md`, `staffing-sequences.md`, `staffing-api.yml`, and `staffing-technical-design.md`. Both are flagged as Coverage Gaps rather than drafted in full, since they require new aggregate design the team should own deliberately, not a documentation-level fix. Also of note: FDD 15.6/15.11/15.12's own narrative is self-contradictory about whether ID Splitting is a Business-User UI request or an Admin/backend-only task — resolved here by reading the doc's own more specific Addendum (15.11.1), which is unambiguous that splitting is Admin/Mi-Key-backend-only, consistent with Retire. The Mi-Key Interface document is raw REST/JSON contract detail (Boundary Violation, consistent with how FDD 24's review treated the CEPAS interface docs). The Decision Sheet for Link/Split data reconciliation is a mostly-empty template — its three captured pre-decisions are already reflected in 15.6's narrative and add no new content.
