## Summary

This FDD covers the "Add New Employee" entry point on the Staffing Authorized User dashboard: a district user searches for an existing identity, submits demographic data, and the system calls Mi-Key to return Match / No Match (new ID created) / Near Match (requires resolution), after which the employee can proceed to report employment data. **The initial domain guess in the tracker (iam primary, organizations cross-domain) is incorrect and is corrected by this review.** IAM explicitly disclaims ownership of identity matching and Unique ID assignment in its own Scope section ("owned by `identity-resolution`"); the actual SDD implementation of everything this FDD describes — the `EmployeeRoster` aggregate, `ID_RESOLUTION_REQUESTS` entity, the "Add New Employee" sequence, and the "Near Match Resolution" sequence, including the Mi-Key match/no-match/near-match branching, the Identity Admin worklist hand-off, and the district-vs-citizen cross-notification pattern — already lives in `staffing-domain.md` / `staffing-sequences.md` / `staffing-permissions.md`, and was substantially reviewed once already under FDD 10 (`10-staffing-admin.md`, Tagging row for Feature 10.12). IAM is touched only for a single `POST /permissions/check` call; organizations is touched only via the standard entity/scope context pattern used everywhere else. The FDD's own Dependencies section confirms this framing: it names FDD 10 (Staffing Admin) and FDD 21/22 (Employee Roster/Assignment Details) as the domain this process operates inside, and names FDD 15.1-15.5 (the not-yet-reviewed "Identity Management Integration" folder) as the actual source of the Mi-Key mechanics — this document is a thin, staffing-side entry point into that process, not an independent description of it. Net result: the SDD is already well-aligned with this FDD's content on the staffing side. One genuine, decidable discrepancy blocks a clean "Aligned" status (Discrepancy #1, API-channel new-ID creation), plus one internal SDD inconsistency (Discrepancy #2, an "Identity Admin"-only endpoint gated by a Staffing-Data-Admin permission) that both this review and the FDD 10 review before it flag as unresolved pending FDD 15.9's dedicated review of the Identity Administrator role.

**On the FDD 15 overlap question asked directly:** this FDD is a **narrower, staffing-side entry point into the same process FDD 15 will cover in depth**, not a duplicate of it and not something this review should attempt to fully resolve. FDD 24's own Addendum (24.2-24.5) restates a meaningful amount of Near-Match-Resolution and Request-for-ID mechanics that FDD 15.2/15.3 will define in full (match/no-match/near-match handling, "Use this Potential"/"Request New ID" actions, justification-gated admin escalation) — but always from the district/Employee-Roster perspective and always by cross-reference to the 15.x docs for the actual mechanics, never by asserting new mechanics of its own. FDD 15.4 (Person Search) explicitly treats FDD 24 as *its* trigger point ("as defined in 24 - Collection & Compliance - Request for ID.docx"), confirming the two document sets were written as companions, not competitors. This review therefore keeps a light touch on the identity-matching mechanics themselves (Coverage Gaps #1-#2 below) and defers deep design work on Person Search criteria, SSN/demographic validation rules, and the Identity Administrator's full capability surface to the FDD 15 review, consistent with the FDD 10 review's own prior disposition of the same boundary.

## 2. Discrepancies

| # | Shape | Topic | Side A Says (doc:section) | Side B Says (doc:section) | Assessment | Resolution / Decision |
|---|---|---|---|---|---|---|
| 1 | FDD vs. SDD | Whether the real-time API channel may create brand-new Unique IDs | FDD 24 Addendum 24.4.2 (School District local-HR-system API submission): "If the API request is for a new employee (no Unique ID provided), the system must reject the request and return an error code indicating that ID creation must be performed via the UI or a specific ID creation service." | `staffing-api.yml`'s `POST /employee-roster/add-employee`: `x-access: [internal-user, external-client]` with no distinction between the two callers; description states it "Triggers Mi-Key identity matching synchronously" for both, and `staffing-sequences.md`'s "Add New Employee" sequence shows the "No Match (New ID Created)" branch completing automatically (201 Created) with no additional gate — the same as the UI path. | Genuine, decidable conflict — not a terminology issue. The FDD wants the API/external-client channel restricted from ever minting a brand-new Unique ID (only allowed to attach an *existing* one), evidently to keep automated bulk-style integrations from creating identities without a human in the loop; the SDD's endpoint currently treats `internal-user` (UI) and `external-client` (API) identically, so an external HR system can trigger new-ID creation exactly like a UI user can. | **Needs Decision** (internal, not client-blocking — the FDD already states the intended rule plainly). Recommend `staffing-api.yml` add a validation branch for `external-client` callers: reject with a distinguishing error code when no `uniqueId` is supplied and Mi-Key would otherwise return "No Match," directing the caller to the UI or (per FDD 24.4.2's own hedge) "a specific ID creation service" to be defined by FDD 15.5 (Bulk File and API Requirements). Not fixed directly here since it changes endpoint behavior/response contract, not just documentation. |
| 2 | SDD vs. itself | Whether an "Identity Admin" permission actually exists to back the endpoints described as its exclusive domain | `staffing-api.yml`'s `POST /admin/new-id-requests/{requestId}/approve` and `.../deny`: both descriptions state "Identity Admin role only." | Both endpoints' `x-permissions-required` is `staffing.admin.manage-collections` — a Staffing Data Admin permission per `staffing-permissions.md` ("Staffing Data Admin role; create collections, set date ranges, entity types"). No `staffing-permissions.md` or `iam-permissions.md` entry for any "Identity Admin"-specific permission exists anywhere in the SDD, despite "Identity Admin"/`IdentityAdminWorklist` appearing by name in both `staffing-api.yml` and `staffing-sequences.md`. | Real internal inconsistency: the endpoint documentation asserts an actor-level restriction ("Identity Admin only") that the enforced permission doesn't actually implement — anyone with the general Staffing Data Admin permission bundle can currently approve/deny new-ID requests, whether or not they hold whatever "Identity Admin" is actually supposed to be. This mirrors a gap the FDD 10 review already flagged (Coverage Gap #5: "the FDD's broader ask — a dedicated admin config surface for identity-specific validations... isn't distinguished anywhere in the SDD from the general-purpose `staffing.admin.*` permissions"). | **Not resolved here — deferred to the FDD 15 review**, specifically FDD 15.9 (Admin Identity Requirements), which is squarely about defining the Identity Administrator's role, worklist, and permission set (confirmed by reading 15.9 directly: "Identity related authorized user roles and permissions" is explicitly one of its own admin requirements, §"Detailed Requirements for Identity Administrator System Management"). Recommend FDD 15.9's review either introduce a dedicated `staffing.identity-admin.*` (or `identity.*`) permission category and repoint these two endpoints to it, or, if Identity Admin turns out to be a scoped variant of the existing Staffing Data Admin role rather than a separate one, correct the misleading "Identity Admin role only" wording in `staffing-api.yml` to match. No fix made now — inventing the permission category would be exactly the kind of judgment call FDD 15.9's dedicated review should own. |
