## Summary

This is the first review of the `epp` domain, covering both its Admin (FDD 13) and User (FDD 25) sides together since they describe one capability from two angles. The domain's core structure holds up well: `epp-domain.md`'s `EducatorPreparationProvider`, `CandidateEnrollment`, `CredentialApplicationReview`, and `ApprovalApplicationReview` aggregates all map cleanly onto the FDDs' actual screens and workflows, and several previously-open items in `epp-domain.md` are now resolved directly from FDD text (the Reading Diagnostics/Special Ed Director flag purpose, the per-route valid-status-set question, and the Conviction Flag rule's TODO). FDD 13.7 turned out to be the opposite of the expected Boundary Violation: the client's own document states the feature "is no longer needed" because identity management for EPP is now fully covered by FDD 15.0 — it carries no content to review. The most consequential finding is a genuine cross-domain wiring bug: `credentialing-sequences.md`'s "Submit New Certificate Application" sequence called a nonexistent EPP endpoint (`GET /enrollment?educatorId={id}`) instead of the real, already-modeled `GET /candidates/{candidateId}/enrollment-status` in `epp-api.yml` — fixed directly. The single open discrepancy needing a decision is whether "Application Remarks" are required or optional on Hold/Deny/Cancel actions for the *standard* (non-Approval) worklist — FDD 25.3.1's Addendum explicitly says optional, while `epp-domain.md`'s own invariant and `epp-sequences.md`'s Hold/Deny sequences require them (consistent with the separate, and FDD-agreed, Approval-tab Deny rule requiring remarks).

## Answers to This Review's Priority Questions

**1. Does `epp-domain.md`/`epp-sequences.md` model a "Recommendation" concept matching how
FDD 13/25 describe it?** **Yes, and it's a strong, near-exact match.** `CredentialApplicationReview`'s
`Recommend` action, its "EPP Recommendation Requires MTTC Pass" and "EPP Recommendation
Triggers Payment (In-State) or OEE Review (Out-of-State)" business rules, and the
`CredentialApplicationRecommended` event all match FDD 25.1/25.3's description precisely —
including the specific in-state/out-of-state routing split (Pending Payment vs. direct-to-OEE),
the endorsement-selection grid, and the MTTC-pass validation with an Alternative Pass override.
The separate `ApprovalApplicationReview` aggregate for alternative-route Approval applications
(returns to ISD worklist on both Recommend and Deny, never routes to state approval directly)
is also modeled and matches FDD 25.1/25.3's Approval-tab description exactly, including the
Deny-requires-remarks / Recommend-remarks-optional asymmetry. This is the domain's central
cross-domain integration point and it is solidly modeled; the one real gap found (a wrong
endpoint name in `credentialing-sequences.md`) has been fixed directly (Discrepancy #2).

**2. Does FDD 13.7 confirm EPP as a MiLogin-for-Business actor type consistent with FDD 01's
finding?** **FDD 13.7 itself adds no evidence either way — it is a one-paragraph stub stating
the feature "is no longer necessary" because identity management for EPP is fully covered by
FDD 15.0 (Identity Management Integration).** It was reviewed in full but contains no
functional content to compare. However, FDD 01's own source text (independently re-confirmed
during this review) directly states: "MiLogin for Business Users include School Districts...
EPPs and Professional Learning Sponsors" and "EPPs receive entity level access and must
receive approval from the designated individual within EEM" — and `iam-domain.md`'s `Scope`
value object already lists `EPP` as a valid `scope_type` alongside `Building`/`District`/`ISD`/
`PLS`/`Nonpublic`/`System`. So the underlying fact FDD 01's review found is independently
confirmed and already correctly reflected in the SDD; FDD 13.7 simply doesn't speak to it.

**3. Does anything here inform whether `CredentialApplication`'s eligibility checks for
program-enrollment-dependent permit types correctly integrate with EPP data?** **Partially,
and it surfaced one real bug (now fixed) plus one remaining gap worth flagging.** The bug:
`credentialing-sequences.md`'s "Submit New Certificate Application" sequence called a
nonexistent EPP endpoint; the real, fully-specified endpoint (`GET /candidates/{candidateId}/
enrollment-status`, internal-service/mTLS) already exists in `epp-api.yml` and is now wired up
correctly (Discrepancy #2). The remaining gap: `credentialing-sequences.md`'s "Submit Permit
Application" sequence (the standard intake path for Full Year Basic Substitute and other
program-enrollment-dependent permits, per the 17 review) validates permit eligibility via the
Business Rule Engine and an unconfirmed Staffing employment-assignment check, but never calls
EPP's enrollment-status endpoint at all — unlike "Submit New Certificate Application," which
does. Since `credentialing-domain.md`'s generic `RequirementRule` explicitly lists "program
enrollment" as an eligibility criterion example, this looks like an omission rather than a
deliberate exclusion, but confirming exactly which permit types require an EPP check (as
opposed to certificates only) is a judgment call outside this review's source documents —
flagged here for whoever next touches "Submit Permit Application," not fixed speculatively.

## Process/Template Friction Noted

- This review's most notable surprise was FDD 13.7 being the *opposite* of the expected
  Boundary Violation candidate: rather than over-specifying a technical integration contract
  (the pattern seen in every other "*.7"/"Identity Management Integration"-named document in
  this corpus so far), it explicitly retracts itself in one sentence. Worth keeping in mind for
  future reviews that a document's naming pattern predicts its *topic*, not reliably its
  *disposition* — some client documents in this numbering series turn out to be intentional
  stubs once a capability was consolidated elsewhere (FDD 16 in the 11 review was a similar
  case). Recommend treating any very short FDD document as a signal to check for a
  self-superseding disposition before assuming it needs a full four-section review.
- The FDD 13/Addendum-13.6 self-contradiction (Discrepancy #1) is the same shape as FDD 13.7's
  self-retraction but *without* an explicit "this is retracted" statement — the Addendum simply
  narrows scope without acknowledging the main narrative said otherwise. Worth a lightweight
  habit for future reviews: when a document's Addendum section describes a feature more
  narrowly than its own main Business Specifications, treat that as a same-document
  discrepancy worth flagging (as done here) rather than assuming the Addendum is simply
  "more detail" on the same scope.
