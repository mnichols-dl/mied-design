# Question Set Updates (staging)

Staged on 2026-10-05. Nothing here has been merged into the live working docs. This folder holds (1) a draft doc set for Question Sets as a platform capability and (2) a recommended-change list for each affected solution area, so the changes can be reviewed and applied one area at a time.

## Recommendation in one paragraph

Make Question Sets a **platform capability** (identifier `questionsets`, prefix `qset:`, already reserved in `design/CONVENTIONS.md`), not a domain. A question set is a means to an end: it collects, validates, versions and stores answers for a business process. It does not decide what a cert application requires or what happens when a requirement is unmet. That logic (requirement types, unmet outcome of block / follow-up / specialist review, reviewer routing, review-before-payment) stays in the consuming domain, which today is Credentialing. This matches how Documents is classified ("the how and where, not the what and why"), and it matches assumptions already in the docs: Professional Learning treats Question Sets as a cross-cutting capability, and PPR says it would consume one ("decision pending architecture review").

## Conventions followed

- Capability doc set follows the existing shape (`-capability.md`, `-technical-design.md`, `-sequences.md`, `-permissions.md`, `-api.yml`) and the templates in `design/working-docs/docs/templates/`.
- Open questions, decisions and backlog items are not written into these drafts. Each draft carries a short pointer list to entries in [tracking-proposals.md](tracking-proposals.md), which is the staging copy of what should be added to `hub/tracking/` and `hub/DECISIONS.md`.
- The graph (`design/graph/MiEdWorkforce.ttl`) is edited through the Solution Design Editor, so graph changes are listed as recommendations only.
- Two autogenerated solution-level files (the capability catalog in `solution-architecture.md` and `solution-api-catalog.md`) are not hand-edited; they regenerate from the new capability and API files.

## Assumptions made (confirm or correct)

1. Capability name stays "Question Sets" with identifier `questionsets`. The word "dataset" is avoided for option lists because Reporting already uses it for Power BI; the draft uses **Option List**.
2. The BRM / rules engine question (FDD 4.2) is not solved here. The draft keeps requirement evaluation inside Credentialing for now and records that as a decision to make (see 01).
3. Question Sets own the form-level "halt with message" behavior (an answer that ends the form with an admin-authored message). The consuming domain decides what a halt means for its process.
4. Consumers create response requests service-to-service; applicants answer through the capability's own runtime API. A proxy-through-consumer alternative is recorded as an open question.
