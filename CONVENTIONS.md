# MiEdWorkforce conventions

This file is the single source of truth for naming/IRI conventions across the
MiEdWorkforce solution design, so that ~35 bounded contexts modeled at different times
(originally converted independently, in parallel, by separate agents) come out looking
like one project rather than many. Read this before adding anything to
`solution/MiEdWorkforce.ttl`. If you find yourself inventing a new prefix, a new stub IRI
for a domain someone else owns, or a new naming pattern not covered here — stop and use
what's below instead, or flag it rather than improvising silently.

**How this file is actually edited.** `solution/MiEdWorkforce.ttl` is generated by the
Solution Design Editor's Save (see the file's own header comment) — the normal way to
change it is through the editor, not by hand-appending Turtle. The conventions below
(prefixes, naming patterns, permission-ID ownership) still govern what gets typed into
the editor's forms; they are no longer about file/directory layout, since everything
lives in that one file.

## Ontology

`ontology/solution-design.ontology.ttl` (repo root), version 0.5. Read it in full before
adding anything — it has extensive comments explaining intent, not just shapes. Some
properties worth knowing about up front, since they're easy to miss on a skim:
- `sd:Solution` — one root instance (`mied:MiEdWorkforce`), `sd:hasBoundedContext`
  linking every domain.
- `sd:cedsAlignment` — reused string property (no fixed domain) for when an
  Aggregate/DomainEntity/ValueObject's *whole shape* maps to a standardized CEDS
  element. Only assert it on real, confirmed alignment — do not guess. Most domains
  will have zero or very few of these.
- `sd:consumesShape` / `sd:producesShape` / `sd:projection` on `sd:ApiOperation` — link
  request/response to the domain-model entity it derives from, instead of restating the
  shape as opaque text. `sd:requestBodySchema`/`sd:responseSchema` are an ESCAPE HATCH
  for the minority of operations that don't map to one entity — do not use them as the
  default.
- `sd:requiresAuth` (boolean) — only assert `false`, and only for genuinely
  unauthenticated public endpoints. Never assert `true` (that's the default).
- `sd:tags` on `sd:ApiOperation` — reused from the source OpenAPI `tags:` grouping.
- `sd:BatchJob` now `rdfs:subClassOf sd:Sequence` (not a bare `sd:BehaviorElement`) —
  inherits `sd:content`/`sd:belongsToContext`/`sd:initiatedBy`/`sd:errorScenarios`/etc.
  Model a domain's scheduled/batch processes (from its `*-technical-design.md`) as
  `sd:BatchJob`, not `sd:TechnicalProcess`, when they run on a schedule/trigger rather
  than describing a one-off algorithm.
- `sd:initiatedBy` on every `sd:Sequence` (including `BatchJob`) — `"user"` |
  `"internal-system"` | `"external-system"`. Assert it on every sequence you convert.
- `sd:Requirement` — Phase 2 only (FDD ingestion). Not used in Phase 1 domain
  conversions; ignore for this pass.
- `sd:BusinessRule` and `sd:Annotation` exist since v0.3 but were **never used** in the
  v1 conversion for ANY domain except credentialing's later v2 pass. Populating them
  properly (from each domain's Business Rules and Open Questions sections) is one of
  the main things this v3 pass adds over v1 — don't skip it.

## Editing existing content: extend, don't restart

The graph already has substantial modeling for every domain listed below — most of
what looks missing is either modeled slightly differently than you'd expect, or
genuinely absent (see `review/GAPS.md` before assuming a gap is new). Read what's
already there for a domain before adding to it.

- **Keep existing IRIs stable.** Every Aggregate, DomainEntity, ValueObject, Permission,
  ApiOperation, DomainEvent, and Sequence already minted is very likely referenced by
  name from another domain's own content (e.g. credentialing references
  `pay:PaymentCompletedEvent`, `staff:StaffingContext`, etc.) — renaming one breaks
  those cross-references invisibly (RDF won't error, it'll just silently stop
  resolving).
- If you find an actual error in existing content (a dangling reference, a typo, an
  `sd:accessType` that should now be multi-valued), fix it and say so — in the node's
  own `sd:notes`, or in `review/PO-FEEDBACK.md`/`review/DESIGN-SPIKES.md` if it needs a
  decision rather than a direct edit.

## Where things live

Everything is one file: `solution/MiEdWorkforce.ttl`. It's generated by the Solution
Design Editor's Save — don't hand-append Turtle to it expecting a stable diff; edit
through the editor (or, for bulk/scripted changes, load it, mutate, and let the editor's
save path re-serialize it) so IRI stabilization and formatting stay consistent.

## Naming pattern per class (local names within your own domain's prefix)

Match this exactly — this is the main thing a later consistency pass checks for:

| Class | Pattern | Example |
|---|---|---|
| `sd:BoundedContext` (your own, the real one) | `<Domain>Context` | `cred:CredentialingContext` |
| `sd:Aggregate` | `<RootEntityName>Aggregate` | `cred:CredentialApplicationAggregate` |
| `sd:DomainEntity` / `sd:ValueObject` | plain descriptive PascalCase, no prefix marker | `cred:CredentialCategory` |
| `sd:StateDefinition` | `<AggregateAbbrev>State_<StateName>` | `cred:AppState_Draft` |
| `sd:DomainEvent` | `<EventName>Event` | `cred:CredentialIssuedEvent` |
| `sd:PermissionCategory` | `Cat_<CategoryName>` | `cred:Cat_CredentialManagement` |
| `sd:Permission` | `Perm_<PermissionName>` | `cred:Perm_ApplicationApprove` |
| `sd:ApiSpec` | `ApiSpec` (one per domain, no suffix needed) | `cred:ApiSpec` |
| `sd:ApiOperation` | `Op_<OperationName>` | `cred:Op_SubmitApplication` |
| `sd:Sequence` | `Seq_<SequenceName>` | `cred:Seq_RenewCredential` |
| `sd:BatchJob` | `BatchJob_<Name>` (full word, not abbreviated — it's a `Sequence` subclass but visually distinct enough to spell out) | `cred:BatchJob_CredentialExpirationProcessing` |
| `sd:BusinessRule` | `Rule_<RuleName>` | `cred:Rule_AutoApprovalCriteria` |
| `sd:TechnicalProcess` | `TP_<ProcessName>` | `cred:TP_CertificatePdfGeneration` |
| `sd:Annotation` | `Question_<Topic>` | `cred:Question_PPRCheckTiming` |
| `sd:SourceDocument` | `<Doc>Doc` | `cred:DomainDoc`, `cred:TechnicalDesignDoc` |

Rules of thumb, not initials: `Perm_`/`Seq_`/`Op_`/`Cat_`/`Rule_`/`TP_` are truncations
of the class name, not acronyms — this is why `BR_` and `OQ_`/`OTQ_` got renamed to
`Rule_`/`Question_` in an earlier pass. If you're about to mint an initialism prefix,
use a truncation instead.

## `sd:permissionId` prefix order: whose permission is this, structurally?

`sd:permissionId` is a dotted string (`<prefix>.<resource>.<verb>`), and the first
segment is a real design decision, not just cosmetics — it says which bounded context
is expected to own, define, and evolve that permission. Two shapes are both valid,
depending on who actually owns the `sd:ApiOperation` the permission gates:

- **Domain-first** (`<owning-domain>.<resource>.<verb>`, e.g.
  `cred:Perm_ApplicationApprove` → `credentialing.application.approve`) — the default,
  for a domain's own permissions on its own operations. The domain that defines the
  operation also defines and owns the permission gating it.
- **Capability-first** (`<cross-cutting-capability>.<domain>-<resource>.<verb>`, e.g.
  `reporting.staffing-reports.manage`, `communications.staffing-templates.manage`) —
  for a cross-cutting capability (Reporting, Communications, ...) minting a permission
  *on behalf of* another domain, when the `sd:ApiOperation` being gated is owned by the
  capability, not the domain. Use this whenever the operation and the permission would
  otherwise belong to different owning contexts — collocating them under the
  capability's own prefix means that capability shows everything its own operations
  could ever require, without cross-referencing every domain that uses it.
  Tag each such permission with two properties (added 2026-09-04): `sd:appliesToDomain`
  pointing at the CAPABILITY's own `sd:BoundedContext` (who owns/defines the
  permission — e.g. `rpt:ReportingContext`, the same value for every permission in that
  capability's file) and `sd:concernsDomain` pointing at the domain whose resource it
  actually gates (e.g. `staff:StaffingContext` — this is the one that varies per
  permission). A domain's own native permission on its own operation only needs
  `sd:appliesToDomain` (pointing at itself) since owner and subject are the same
  context there. "Every permission relevant to domain X" queries should match on
  `sd:concernsDomain` (falling back to `sd:appliesToDomain` when absent), not on
  guessing from the permissionId string's prefix.

**Decided 2026-09-04**: Reporting's per-domain report-viewing permissions were moved
from domain-first (`credentialing.reports.view`, owned by Credentialing) to
capability-first (`reporting.credentialing-reports.view`, owned by Reporting), matching
the shape Communications' template permissions already used — see
`review/PO-FEEDBACK.md`'s FDD 06 section for the reasoning that led here. Don't confuse
this with a domain's own **native** reporting/export features on its own data (e.g.
`iam.reports.view` gating IAM's own generated New-Users/Denied-Requests/Inactivity
reports, or `profpractice.report.view` gating PPR report data) — those stay
domain-first; they were never part of the cross-cutting Reporting capability's Power BI
catalog to begin with, and renaming them would incorrectly imply they were.

`sd:Dependency` / `sd:PermissionRequirement` / `sd:DataRelationship` / `sd:SequenceReference`
instances are `sd:RelationshipNode`s — author them as **blank nodes** (`[] a sd:Dependency ; ...`),
never minted IRIs. This is explicit in the ontology's own comment on `sd:RelationshipNode`.

## Style

- Document scope decisions (which stubs, what's deliberately NOT modeled and why) on
  the relevant node's own `sd:notes` — there's no per-domain file to put a header
  comment in anymore, so the decision needs to live on the graph node itself, or in
  `review/PO-FEEDBACK.md`/`review/DESIGN-SPIKES.md` if it's still open.
- Prefer honest gaps over fabrication: if a source doc references something that
  doesn't exist elsewhere, or a business rule that contradicts another domain's
  content, say so in `sd:notes` (or an `sd:Annotation` if it's substantial) rather than
  inventing a resolution.
- Validate before considering an edit done: the whole graph must parse with oxigraph
  and every object-property target must resolve to something typed. See "Validation"
  below.

## Validation

Node's `oxigraph` package is available at `editor/node_modules/oxigraph` (i.e. run node
from the `editor/` directory). Load the ontology, the shapes, and the solution file, and
confirm:
1. It parses as valid Turtle.
2. No object-property value (`sd:satisfiedBy`, `oa:hasTarget`, `sd:enforcedBy`,
   `sd:appliesTo`, `sd:references`, `sd:viaOperation`, `sd:viaEvent`, `sd:exposedBy`,
   `sd:hasScope`, `sd:hasCategory`, etc.) is untyped (i.e. points at something nobody
   ever declared `a sd:SomeClass`) — that means a typo'd IRI or a missing stub.

Validation snippet (run from `editor/`, e.g. `node -e "..."` or as a `.js` file):

```js
const oxigraph = require('oxigraph');
const fs = require('fs');
const store = new oxigraph.Store();
const files = [
  '../ontology/solution-design.ontology.ttl',
  '../shapes/solution-design.shapes.ttl',
  '../solutions/MiEdWorkforce/solution/MiEdWorkforce.ttl',
];
for (const f of files) store.load(fs.readFileSync(f, 'utf8'), { format: 'text/turtle', base_iri: 'urn:solutiondesign:instance:' });
```
